## 四、优先级说明

| 优先级 | 含义 | 判定标准 | 执行要求 |
| --- | --- | --- | --- |
| P0 | 阻塞级核心功能 | 直接对应需求中的 P0 项；失败将导致主要使用场景不可用、数据丢失或安全风险 | 每次构建必测，任一失败即阻断发布 |
| P1 | 重要功能 | 影响体验完整性与扩展能力（如扩展语法、导入导出细节、快捷键自定义） | 每轮回归必测，允许在发布说明中给出已知问题 |
| P2 | 次要功能与预留能力 | 本期为 P2 或仅预留接口的需求（如图床集成、HTML/Word 导入转换） | 按用例中的指定方式校验预留情况，不作为发布阻断项 |

用例编号规则：`TC-<需求域前缀>-<三位序号>`，各组从 `001` 起连续编号，不跳号、不重复。

## 七、执行与判定说明

1. 执行顺序建议：先执行 `TC-INSTALL` 确认安装与启动基线，再按 `TC-EDIT` → `TC-SYNTAX` → `TC-FILE` → `TC-EXPORT` → `TC-THEME` → `TC-IMAGE` → `TC-KEY` → `TC-SEC` → `TC-PERF` 的顺序回归。
2. 判定规则：预期结果中的具体数值（如 500 ms、16 ms、300 MB、120 MB、16000 px、`0.3`、`100%`）为验收阈值，实测需满足或优于阈值方可判为通过。
3. 提示文案判定：涉及提示文案的用例，以本清单中引用源码的原文为准；文案逐字一致方为通过，仅语义接近判为不通过。
4. P2 与预留能力判定：图床集成（F-44）与 HTML/Word 导入转换按各自用例中约定的方式判定，不得以「功能未实现」直接判为缺陷，也不得编造未提供的功能作为通过依据。
5. 环境覆盖要求：ENV-01 ~ ENV-34 中标注「全组」的环境需完整执行全部用例，其余环境至少完整执行「必测组」列出的用例组。
6. 缺陷记录要求：失败用例需记录环境编号、实际结果、复现步骤、日志文件路径与截图；涉及数据损坏、脚本执行、数据外传的失败一律按最高等级缺陷处理。
